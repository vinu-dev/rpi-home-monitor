# Feature Spec: Local CA Client-Certificate Authentication

Tracking issue: not assigned. Branch: `docs/local-ca-mtls-design`.
Status: Draft for review. Design only, no implementation in this branch.

## Title

Replace shared/default setup passwords with a local, offline certificate
authority model for RPI local GUI authentication, first-boot provisioning, and
service access.

## Goal

An operator can run a private local CA, with no public CA and no online CA
service, and use it to issue:

- one HTTPS/server certificate per RPI
- one client certificate per service laptop, mobile device, or human user
- optional signed work-order tokens for device-bound setup jobs

The RPI local GUI accepts access only when the connecting browser presents a
client certificate that chains to the trusted local CA and carries a profile
that authorizes the requested action.

The result should satisfy these product constraints:

- no shared RPI GUI password
- no factory/default GUI password
- no RPI-generated OTP for setup login
- offline validation before internet or backend access exists
- clear user roles after setup
- auditable service and owner actions
- no authentication backdoor that bypasses the primary auth model

## Non-Goals

- Implementing the feature in this branch.
- Creating production CA private keys or storing real certificates in the repo.
- Depending on an online/public CA.
- Depending on a cloud identity provider for first setup.
- Adding SSH, CLI, localhost, or hidden recovery bypasses.
- Solving lost-sole-admin recovery with software. That remains hardware reset
  or SD-card reflash per ADR-0022.
- Making mobile client-certificate UX the primary supported path before
  browser/device testing proves it is reliable.

## Concepts

### Certificate Authority

A certificate authority signs certificates. If a device trusts the CA public
certificate, it can verify that another certificate was issued by that CA.

For this design, the CA is private and local. It is not a public internet CA.
It can be a secure laptop, offline VM, or small internal signing machine. The
important rule is that the CA private key is protected and never copied to an
RPI, browser, mobile phone, repository, image artifact, or support bundle.

### Trust Anchor

The trust anchor is the public CA certificate installed on devices that should
trust the CA's issued certificates.

The same local CA public certificate can be installed on:

- RPI images, so RPIs trust laptop/mobile/user client certificates
- service laptops and mobiles, so browsers trust RPI HTTPS certificates

### Server Certificate

An RPI server certificate proves the browser is talking to the expected RPI GUI.
It is presented by the RPI during HTTPS.

The RPI server certificate needs a Subject Alternative Name that matches how
the service person opens the GUI. A certificate for `rpi-001.local` will not
cleanly validate if the browser opens `https://192.168.1.245/` unless that IP
address is also in the certificate SAN.

### Client Certificate

A client certificate proves the browser, laptop, mobile, or user is authorized
to connect. It is presented by the browser during the TLS handshake.

Client certificates must be unique per person/device. The product should not
ship one shared service certificate.

### mTLS

Mutual TLS means both sides authenticate with certificates:

- browser validates the RPI server certificate
- RPI validates the browser/client certificate

### Certificate Profile

A certificate profile describes what a certificate is for. The RPI should not
trust a certificate only because it chains to the local CA. It must also check
that the certificate is intended for this product and role.

Examples:

- `setup-provisioner`
- `owner-admin`
- `viewer`
- `service-maintenance`
- `read-only-support`
- `backend-registrar`

### Work-Order Token

A work-order token is an optional signed JSON document issued by the local
provisioning process. It binds a service action to one RPI, one technician
certificate, and one job.

It is not generated by the RPI and is not an OTP. It is offline authorization
evidence that the RPI can verify with a public signing key.

## Current System Context

The current server GUI already terminates HTTPS in nginx at
`app/server/config/nginx-monitor.conf`.

Current operator login is Flask session and password based in
`app/server/monitor/auth.py`.

Current first-boot setup logic lives in `app/server/monitor/provisioning.py` and
`app/server/monitor/services/provisioning_service.py`. The setup endpoints are
currently reachable while setup is incomplete, rate-limited, and blocked after
setup completion.

The camera side already contains a useful pattern: human status is served on
the browser-facing status listener, while server-only camera control uses a
dedicated mTLS listener in `app/camera/camera_streamer/control_server.py`.

ADR-0022 forbids backdoor authentication or recovery mechanisms. This design
stays compatible with that rule only if certificate auth becomes the primary
auth mechanism for the setup/service surface. It must not be a hidden bypass
around normal admin login.

## Design Summary

Use a private local CA as the shared trust root.

```text
                           Local Offline CA
                         ca.crt + ca.key
                              |
              +---------------+----------------+
              |                                |
       signs RPI HTTPS certs           signs client certs
              |                                |
              v                                v
     RPI presents server.crt        Laptop/mobile presents client.crt
              |                                |
              +---------------+----------------+
                              |
                              v
                    HTTPS local GUI with mTLS
```

Each RPI image trusts the local CA public certificate. Each service/user device
also trusts the same local CA public certificate.

When a browser opens the RPI GUI:

1. RPI presents its HTTPS certificate.
2. Browser verifies the RPI certificate chains to the local CA.
3. RPI asks for a client certificate.
4. Browser presents a laptop/mobile/user certificate.
5. nginx verifies the client certificate chains to the local CA.
6. Flask checks purpose, profile, local allow/deny state, setup/service mode,
   and action authorization.
7. Flask creates a short cert-bound session or requires the certificate on
   every privileged request.

## Certificate And Key Storage

### Local CA Machine

The CA machine is the only place the CA private key lives.

```text
local-ca/
  private/
    home-monitor-local-ca.key        # secret, never copied to RPI
  public/
    home-monitor-local-ca.crt        # public trust anchor
  issued/
    rpi/
      rpi-001.server.crt
      rpi-002.server.crt
    clients/
      vinu-laptop.client.crt
      vinu-mobile.client.crt
      service-laptop-01.client.crt
  packages/
    vinu-laptop.client.p12
    vinu-mobile.client.p12
```

### RPI

The RPI stores only its own private key and public certificates.

```text
/etc/monitor/trust/
  local-ca.crt                       # public CA cert trusted for client auth

/data/certs/
  server.key                         # RPI HTTPS private key
  server.crt                         # RPI HTTPS cert signed by local CA

/data/config/
  cert-users.json                    # local certificate user/role records
  cert-denylist.json                 # optional denied cert fingerprints/serials
  work-order-used.json               # optional consumed work-order IDs
  last-good-time                     # optional trusted time floor
```

The RPI must never contain:

- local CA private key
- client private keys for users
- shared service certificate private keys

### Service Laptop Or Mobile

The service/user device stores:

```text
trusted roots:
  home-monitor-local-ca.crt          # lets browser trust RPI HTTPS certs

personal certificates:
  service-laptop-01.client.p12       # client private key + client cert
```

For best security, the client private key should be non-exportable or backed by
OS keychain, TPM, Secure Enclave, or a hardware token.

## Certificate Types

### RPI HTTPS Certificate

Purpose:

- server authentication
- lets laptop/mobile verify it is connected to the expected RPI

Required properties:

- chains to local CA
- Extended Key Usage: `serverAuth`
- SAN includes the name used in browser
- unique key per RPI

Recommended SAN pattern:

```text
DNS:rpi-001.local
DNS:rpi-001
DNS:rpi-divinu-001.local
```

IP SANs can be added only when the IP is known and stable:

```text
IP:192.168.1.245
```

If DHCP changes the address, IP-based browser trust breaks. A stable hostname
is the cleaner path.

### Laptop/Mobile/User Client Certificate

Purpose:

- client authentication
- identifies the service laptop, mobile, or user
- carries setup/service/owner role

Required properties:

- chains to local CA
- Extended Key Usage: `clientAuth`
- product purpose extension or certificate policy
- role/profile extension or certificate policy
- unique serial/fingerprint per user/device

Example identity fields:

```text
Subject CN: service-laptop-01
Subject O: Home Monitor Local Service
SAN URI: urn:home-monitor:client:service-laptop-01
Policy OID: home-monitor.profile.setup-provisioner
```

The RPI must not authorize by common name alone. CN strings are display labels,
not authorization policy.

## Local CA Workflow

### One-Time CA Creation

1. Create a local root CA or local root plus issuing intermediate.
2. Protect the CA private key.
3. Export the CA public certificate.
4. Put the CA public certificate into the RPI image.
5. Install the CA public certificate into service laptop/mobile trust stores.

Recommended hierarchy:

```text
Home Monitor Local Root CA
  |
  +-- Home Monitor RPI Server Issuing CA
  |
  +-- Home Monitor Client Auth Issuing CA
```

This separation is cleaner than one flat CA because server certificates and
client certificates can have separate profiles and constraints.

For a small lab, a single local root can work, but the implementation must
still enforce `serverAuth` versus `clientAuth` and product-specific profiles.

### Per-RPI Certificate Issue

For each RPI:

1. Choose a device ID, for example `rpi-001`.
2. Create an RPI private key.
3. Create a certificate signing request with SANs.
4. Sign the CSR using the local CA.
5. Copy `server.key`, `server.crt`, and `local-ca.crt` onto the RPI.
6. Record the issued cert serial/fingerprint in the CA inventory.

Best security: create the private key on the RPI or directly on the SD card's
data partition, not on the CA machine. The CA machine signs a CSR and never
sees the RPI private key.

### Per-Laptop/Mobile Certificate Issue

For each service laptop/mobile/user:

1. Choose a certificate identity, for example `service-laptop-01`.
2. Choose a role/profile.
3. Generate a private key.
4. Sign the client certificate using the local CA.
5. Export a `.p12/.pfx` for browser installation.
6. Import it into the device certificate store.
7. Delete temporary export files after installation.
8. Record serial/fingerprint, owner, role, issue date, and expiry in CA
   inventory.

Do not share one `.p12` across several laptops or users.

## Laptop And Mobile Installation

### Windows Service Laptop

1. Install `home-monitor-local-ca.crt` into Trusted Root Certification
   Authorities or the appropriate enterprise trust store.
2. Install `service-laptop-01.client.p12` into Current User Personal
   Certificates.
3. Mark the private key non-exportable where possible.
4. Use Edge or Chrome. The browser should prompt for the client certificate
   when opening the RPI GUI.

### macOS Service Laptop

1. Import `home-monitor-local-ca.crt` into System or login Keychain and mark it
   trusted for TLS.
2. Import the `.p12` into login Keychain.
3. Use Safari, Chrome, or Edge.

### Linux Service Laptop

1. Install the CA public certificate into system trust if the browser uses it.
2. For Firefox, import the CA and `.p12` into the Firefox/NSS certificate store.
3. For Chrome/Chromium, use system or NSS store depending on distro.

### iOS

1. Use a signed `.mobileconfig` profile containing the CA trust and client
   identity.
2. Install profile.
3. Enable trust for the CA certificate.
4. Use Safari for testing.

### Android

1. Install the CA certificate as a trusted user CA if browser policy allows it.
2. Install the `.p12` as a user credential.
3. Test Chrome behavior on target Android version.

Mobile client-certificate UX varies by browser and OS. The design supports it,
but release readiness should require device-specific testing before promising
mobile as the primary service path.

## First-Boot Workflow After Flashing SD Card

### Preferred Pre-Provisioned SD Workflow

This gives the cleanest browser trust.

```text
CA machine/signing workstation
  |
  | 1. create per-RPI key/CSR/cert or sign CSR
  v
SD card data partition
  |
  | 2. copy server.key/server.crt/local-ca.crt
  v
RPI first boot
  |
  | 3. starts setup hotspot and HTTPS GUI
  v
Service laptop joins hotspot
  |
  | 4. opens https://rpi-001.local or setup IP
  v
Browser and RPI perform mTLS
  |
  | 5. setup UI opens only for authorized cert profile
  v
Wi-Fi/proxy/backend/owner setup
```

Detailed sequence:

1. Operator flashes SD card.
2. Operator mounts the writable data/config partition, or uses a provisioning
   script that writes to the expected first-boot files.
3. Script writes:
   - `/data/certs/server.key`
   - `/data/certs/server.crt`
   - `/etc/monitor/trust/local-ca.crt` or image-bundled equivalent
   - optional `/data/config/cert-users.json`
4. RPI boots.
5. RPI starts setup hotspot.
6. nginx starts HTTPS with the CA-signed RPI certificate.
7. Service laptop joins hotspot.
8. Service laptop opens the setup URL.
9. Browser validates the RPI cert.
10. RPI requests client certificate.
11. Browser presents service client certificate.
12. RPI validates client certificate chain and profile.
13. RPI serves the setup GUI.

### CSR-On-First-Boot Workflow

This keeps the RPI private key on the RPI, but the first browser connection is
less clean unless a temporary factory trust path exists.

```text
RPI first boot
  |
  | generates server.key + server.csr
  v
temporary setup HTTPS
  |
  | service laptop downloads CSR or reads it from SD/USB
  v
local CA signs CSR offline
  |
  | service laptop uploads server.crt
  v
RPI restarts HTTPS with trusted cert
```

### Implemented GUI HTTPS Certificate Separation

The passwordless/admin-certificate branch keeps browser HTTPS trust separate
from camera streaming trust.

```text
Browser GUI HTTPS:
  /data/certs/gui-server.crt
  /data/certs/gui-server.key
  used by nginx on 443 and 9443
  optional local-CA-signed certificate installed through setup

Camera RTSPS and camera control:
  /data/certs/server.crt
  /data/certs/server.key
  used by MediaMTX/camera trust paths
  not replaced by the GUI certificate flow
```

On first boot and OTA upgrade, `home-monitor-gui-cert-bootstrap.service` copies
the existing `server.crt` and `server.key` to `gui-server.crt` and
`gui-server.key` when no GUI certificate exists. This makes the new nginx
configuration boot-safe while preserving the current camera certificate model.

During certificate-protected setup, the operator may choose an optional
Trusted Browser Certificate step:

1. RPI generates `/data/certs/gui-server.key` locally.
2. RPI creates `/data/certs/gui-server.csr` with DNS/IP SANs.
3. Service laptop downloads the CSR.
4. The separate private CA generator signs the CSR with `sign-rpi-csr`.
5. Service laptop uploads only `gui-server.crt` back to the RPI.
6. RPI validates that the cert matches the local private key, chains to the
   trusted local CA, has `serverAuth`, has SANs, is time-valid, and then reloads
   nginx through the privileged helper.

The CA generator must not receive or store `gui-server.key` in this flow.

This workflow is acceptable for lab use if the operator verifies a displayed
fingerprint over a physical/local channel. It is weaker than pre-provisioning
because the first browser session cannot be fully authenticated by the local CA.

### Temporary Self-Signed Fallback

If neither pre-provisioning nor CSR transfer is available:

1. RPI boots with temporary self-signed cert.
2. Service laptop sees browser warning.
3. Technician confirms physical device/fingerprint.
4. Technician uploads CA-signed server cert.
5. RPI switches to trusted cert.

This should be treated as a fallback, not the preferred production workflow.

## Setup Hotspot UX

The HTTP surface on the hotspot must remain non-sensitive.

Allowed HTTP behavior:

- captive portal detection redirect
- static instruction page
- link to HTTPS setup URL
- generic "service certificate required" explanation

Disallowed HTTP behavior:

- Wi-Fi credential submission
- admin/user setup
- certificate upload with secrets
- backend registration
- diagnostic export
- any action that changes state

The real setup GUI is HTTPS plus client certificate.

```text
Phone/laptop joins hotspot
  |
  +-- http://192.168.4.1
  |     |
  |     +-- only shows "open HTTPS setup" guidance
  |
  +-- https://rpi-001.local
        |
        +-- mTLS required
        +-- setup actions allowed by cert role
```

## Request Authentication Flow

```text
Browser
  |
  | HTTPS request
  | client certificate offered
  v
nginx :443
  |
  | verifies TLS chain against local-ca.crt
  | sets trusted headers
  v
Flask app on 127.0.0.1:5000
  |
  | parses cert metadata
  | checks profile, role, time, setup/service state
  | checks local allow/deny
  v
Route decorator
  |
  | permits or denies action
  v
Service layer
  |
  | performs business logic
  | writes audit event
```

nginx should overwrite any incoming certificate headers before proxying to
Flask. Flask must trust certificate headers only because the app is reachable
through localhost from nginx, not directly from the LAN.

## Session Model

Two modes are possible.

### Cert Per Request

Every privileged request requires a valid client certificate.

Pros:

- strongest binding between TLS identity and action
- stolen Flask session cookie is less useful

Cons:

- more browser compatibility testing
- harder to support mixed public/authenticated routes

### Cert-Backed Web Session

The certificate is verified at login or first request, then Flask creates a
short session bound to the cert fingerprint.

Session fields:

```json
{
  "auth_method": "client_certificate",
  "cert_fingerprint": "SHA256:...",
  "cert_serial": "...",
  "cert_subject": "...",
  "role": "owner-admin",
  "created_at": 0,
  "last_active": 0
}
```

Pros:

- fits current Flask route/session model
- keeps CSRF behavior familiar
- easier UI implementation

Cons:

- stolen session cookie remains valuable until timeout
- app must invalidate session if cert identity changes

Recommended first implementation: cert-backed web session, with an option to
require cert presence on every sensitive state-changing route.

## User And Role Model

The design separates certificate identity from local authorization.

Certificate identity answers:

- Who is connecting?
- Which CA issued the certificate?
- Which profile did the CA assert?

Local authorization answers:

- Is this certificate still allowed on this RPI?
- Which role does this RPI grant it?
- Is this role allowed to perform this action now?

### Local User Record

Proposed `cert-users.json` shape:

```json
{
  "users": [
    {
      "id": "cert-user-001",
      "display_name": "Vinu laptop",
      "cert_fingerprint": "SHA256:...",
      "cert_serial": "01A2",
      "issuer_fingerprint": "SHA256:...",
      "role": "owner-admin",
      "enabled": true,
      "created_at": "2026-06-03T00:00:00Z",
      "last_seen_at": "",
      "notes": "Initial owner admin certificate"
    }
  ]
}
```

If a cert role from the CA conflicts with local policy, use the lower privilege.

Example:

```text
Certificate profile: service-maintenance
Local role override: read-only-support
Effective role: read-only-support
```

## Role Matrix

```text
+--------------------+--------+-------+----------+-------+------+-------+
| Action             | setup  | owner | service  | view  | ro   | reg   |
+--------------------+--------+-------+----------+-------+------+-------+
| Basic status       | yes    | yes   | yes      | yes   | yes  | yes   |
| Wi-Fi setup        | yes    | yes   | yes*     | no    | no   | no    |
| Proxy setup        | yes    | yes   | yes*     | no    | no   | no    |
| Backend register   | yes    | yes   | yes*     | no    | no   | yes   |
| Add owner cert     | yes**  | yes   | no       | no    | no   | no    |
| Live video         | no     | yes   | no***    | yes   | no   | no    |
| Recordings         | no     | yes   | no***    | yes   | no   | no    |
| Diagnostics        | no     | yes   | yes      | no    | yes  | no    |
| Restart service    | no     | yes   | yes*     | no    | no   | no    |
| Factory reset      | no     | yes   | no       | no    | no   | no    |
| User management    | no     | yes   | no       | no    | no   | no    |
+--------------------+--------+-------+----------+-------+------+-------+

setup   = setup-provisioner
owner   = owner-admin
service = service-maintenance
view    = viewer
ro      = read-only-support
reg     = backend-registrar

*  only while service mode is active or work-order permits it
** only during first setup, to register the first owner-admin certificate
*** allow only if a separate support-video profile is intentionally approved
```

## First Owner Setup

The password step is replaced by owner certificate registration.

Current model:

```text
setup wizard -> set admin password -> setup complete -> login with password
```

Proposed model:

```text
setup wizard -> register owner-admin cert -> setup complete -> login with cert
```

First owner registration options:

1. Upload or present an owner-admin certificate during setup.
2. Use the setup-provisioner certificate as the initial owner only if explicitly
   approved. This is less clean because service and owner identities should be
   separate.
3. Generate a local owner certificate using an operator-held local CA before
   visiting the RPI.

Recommended: create owner/admin client cert outside the RPI and register its
fingerprint during setup.

## After Setup

Normal access:

1. User opens RPI GUI.
2. Browser presents client certificate.
3. RPI verifies certificate.
4. RPI maps fingerprint/profile to role.
5. User sees only allowed pages/actions.

There is no password login page in certificate-only mode.

If the product keeps public share links, they need a separate policy because a
global mTLS requirement on port 443 would block unauthenticated share viewers.
Options:

- disable public share links in certificate-only deployments
- serve public links on a separate hostname or port without client certs
- keep nginx `ssl_verify_client optional` and enforce certs only on protected
  routes

For a pure no-password local appliance, disabling public unauthenticated share
links is the simplest security posture.

## Service Mode Timeout

Setup-provisioner and service-maintenance certificates should not grant broad
post-setup access forever.

Recommended states:

```text
FIRST_BOOT_SETUP
  setup-provisioner allowed for setup actions
  ends when setup-complete stamp is written

NORMAL
  owner/viewer cert roles allowed
  service cert can read basic status only

SERVICE_MODE
  service cert can perform maintenance actions
  requires owner-admin approval, physical action, or signed work-order token
  expires automatically
```

Because this design avoids RPI-generated OTPs, service mode activation should
use one of:

- owner-admin certificate approves service mode in GUI
- physical local action if hardware supports it
- signed offline work-order token bound to the RPI and service certificate

Avoid hidden software commands that enable service mode. That would drift into
ADR-0022 backdoor territory.

## Offline Work-Order Token

The local CA can be offline and still issue signed work orders.

Example work-order payload:

```json
{
  "type": "home-monitor-work-order",
  "version": 1,
  "job_id": "WO-2026-0603-001",
  "device_id": "rpi-001",
  "allowed_cert_fingerprint": "SHA256:...",
  "allowed_actions": [
    "wifi.configure",
    "proxy.configure",
    "backend.register",
    "status.basic"
  ],
  "issued_at": "2026-06-03T10:00:00Z",
  "expires_at": "2026-06-04T10:00:00Z",
  "signed_time": "2026-06-03T10:00:00Z"
}
```

The token is signed by a work-order signing key whose public key is installed
on the RPI.

Benefits:

- limits blast radius if a service cert is broadly trusted
- binds action to one RPI
- gives a job ID for audit
- can carry a signed time claim for first-boot time uncertainty
- does not require internet access

Work-order tokens are recommended for service workflows, but not strictly
required for owner-admin certificate login.

## Time, Expiry, And Revocation Without Online CA

Offline CA means there is no real-time OCSP or online revocation check.

The design must handle this directly.

### Time Problem

An RPI without network or RTC may not know the current time. Certificate expiry
validation depends on time.

Recommended time policy:

1. Set a boot-time floor from image build time.
2. Persist last-known-good time in `/data`.
3. Never allow trusted time to move backwards.
4. If time is uncertain, allow only limited first-setup actions.
5. Use signed work-order time for service jobs when available.
6. Once network time is available, enforce normal certificate validity.

### Expiry Strategy

For local-only deployments:

- owner-admin certs can be medium-lived, for example 1 year
- service certs should be shorter-lived, for example 7 to 30 days
- manufacturing/setup certs should be very short-lived, for example 1 to 7 days
- RPI server certs can be 1 to 5 years, depending on renewal process

Short-lived certs reduce the damage from lost client certificates.

### Revocation Strategy

Without online CA, revocation is update/distribution based.

Options:

- local RPI denylist by cert serial/fingerprint
- signed CRL copied during maintenance
- short-lived service certificates
- work-order token required for service actions

If a laptop cert is compromised, every RPI that trusts the CA remains exposed
until the cert expires or each RPI receives a denylist/CRL update. This is the
main operational cost of offline CA.

## HTTPS By Hostname Versus IP

Opening by IP is technically possible but operationally fragile.

```text
Browser URL: https://192.168.1.245
Server cert SAN must include: IP:192.168.1.245
```

If DHCP changes the RPI IP, the certificate no longer matches.

Preferred:

```text
Browser URL: https://rpi-001.local
Server cert SAN includes: DNS:rpi-001.local
```

The setup page can still show the current IP for troubleshooting, but the main
link should encourage hostname access.

## Nginx Design

nginx remains the TLS termination point.

Conceptual configuration:

```nginx
ssl_certificate     /data/certs/server.crt;
ssl_certificate_key /data/certs/server.key;

ssl_client_certificate /etc/monitor/trust/local-ca.crt;
ssl_verify_client optional;
ssl_verify_depth 2;

proxy_set_header X-Client-Cert-Verify $ssl_client_verify;
proxy_set_header X-Client-Cert $ssl_client_escaped_cert;
proxy_set_header X-Client-Cert-Fingerprint $ssl_client_fingerprint;
proxy_set_header X-Client-Cert-Serial $ssl_client_serial;
proxy_set_header X-Client-Cert-Subject $ssl_client_s_dn;
proxy_set_header X-Client-Cert-Issuer $ssl_client_i_dn;
```

Use `optional` if some routes can be public or if Flask decides route-level
policy. Use `on` only when every HTTPS route requires a client certificate.

For this product, a practical first implementation is:

- HTTPS listener requests client certs globally
- Flask blocks protected routes when cert verification is missing
- HTTP listener stays limited to setup guidance and redirects only

Audit detail should include:

- cert serial
- issuer fingerprint
- display name if locally known

- Wi-Fi passwords
- bearer tokens
- backend registration secrets

## Security Analysis

### Strengths

- No shared RPI password exists to leak.
- No default GUI password exists.
- The RPI can authenticate service laptops offline.
- Roles are cryptographic and local-policy enforced.
- Setup access can be narrow and time-scoped.
- Lost password recovery is no longer the primary access problem.

### Main Risks

#### CA private key compromise

If the local CA private key is compromised, attackers can mint trusted certs.

Controls:

- keep CA private key offline or hardware-backed
- use issuing intermediates
- protect CA backups
- record every issued certificate
- rotate CA if compromised

#### Client certificate theft

If a service laptop `.p12` is stolen, attackers can access RPIs that trust that
certificate profile until expiry or denylist update.

Controls:

- non-exportable private keys
- OS/hardware key protection
- short-lived service certs
- local denylist
- signed work orders for service actions

#### Time uncertainty

If RPI time is wrong, expiry checks are unreliable.

Controls:

- boot-time floor
- last-known-good time
- signed work-order time
- limited action set until time is trusted

#### Browser client-cert UX

Browsers and mobile OSes differ in how they prompt for and remember client
certificates.

Controls:

- make laptop workflow primary
- test target mobile devices before promising mobile support
- provide clear operator runbook

#### Cert profile overreach

A broad service certificate could become an operational backdoor.

Controls:

- profile/action matrix
- service mode timeout
- owner/admin or physical/work-order activation for post-setup maintenance
- audit every service action

## Backdoor Review

This design is acceptable only when certificate authentication is the primary
authentication mechanism for the service/setup surface.

It becomes unacceptable if implemented as:

- a hidden endpoint that bypasses normal auth
- a CLI command that adds trusted certs without primary auth
- a static factory certificate shared by all service laptops
- an always-on service role that can reset owner access after setup

Post-setup service access must be scoped, time-limited, and audited.
